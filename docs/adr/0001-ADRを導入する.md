# 0001: ADR を導入する

- ステータス: 採用
- 決定日: 2026-09-06

## 背景

このリポジトリにはアプリの仕様メモがある一方、設計の選択肢や判断理由を継続して記録する仕組みがない。コードと合わせて判断理由を確認でき、採用した結果も振り返れる記録方法が必要になった。

## 決定と理由

`docs/adr/` に Markdown で ADR を管理し、1 件につき 1 つの設計判断を記録する。ファイル名は `0001-ADRを導入する.md` のように 4 桁連番と日本語のタイトルにする。ステータスは「提案中」「採用」「不採用」の 3 つとし、日付は決定日のみを記載する。

仕様メモには期待する動作を、ADR には背景・決定と理由・検討した代替案・採用後の振り返り・関連リンクを記載する。予想するメリットや懸念は「決定と理由」にまとめ、実際に採用して分かったことは「採用後の振り返り」に追記する。

採用済みの判断を変える場合は新しい ADR を作成し、関連リンクで後継を示す。文書の変更履歴は Git で管理するため、本文には設けない。

コードと判断理由を同じ場所でレビューでき、将来の見直しに代替案や実際の結果を活用できることを期待する。一方、番号・一覧・関連リンクの更新と、採用後の振り返りには手作業が必要になる。現在の規模では専用 CLI や CI チェックを追加せず、共通テンプレートとレビューで運用する。過去の判断は必要になったものから根拠を確認して記録する。

## 検討した代替案

- 仕様メモや PR の説明だけに残す: 文書を増やさずに済むが、判断の経緯や採用後の結果をまとめて探しにくいため選ばない。
- 外部の Wiki や文書サービスにまとめる: 閲覧・編集がしやすい一方、コードの変更と記録の更新が分離するため選ばない。
- 専用の ADR 管理ツールを導入する: 採番などを自動化できるが、現時点ではツールの導入・保守より Markdown で手軽に始めることを優先する。
