# ADR：設計判断の記録

ADR（Architecture Decision Record）には、重要な設計判断の背景・理由・代替案と、採用後の振り返りを残します。機能の仕様は [仕様メモ](../proxy-pdf-app-spec.md)、判断の理由と実際の結果は ADR に記載します。

## 記録する判断

- アプリの構成や責務の境界（例：ブラウザ内処理とサーバー処理の分担）
- 主要ライブラリの採用・変更（例：PDF 生成ライブラリの変更）
- データの保存・共有、プライバシーに関する方針
- PDF の品質・性能など、複数の選択肢やトレードオフがある設計

誤字修正、通常のバグ修正、軽微な UI 調整には不要です。既存 ADR の範囲内の実装変更も、新しい判断がなければ追加しません。1 件につき 1 つの判断を、必要な情報に絞って記載します。

## ファイル名

`docs/adr/0001-ADRを導入する.md` のように、**4 桁の連番＋ハイフン＋日本語のタイトル＋.md** とします。本文も日本語を基本とします。

- 番号は既存の最大番号 + 1 とし、欠番は再利用しません。
- タイトルは判断の内容が分かる短い日本語にします。ADR などの技術用語はそのまま使えます。
- 並行作業で番号が重複した場合は、マージ前に調整します。
- マージ済みの ADR は削除・改番せず残します。

## 作成とレビュー

1. [テンプレート](テンプレート.md)をコピーし、上記のファイル名で保存します。
2. ステータスを「提案中」、決定日を「未決定」にし、背景・決定案と理由・検討した代替案を記載します。予想するメリットや懸念は「決定と理由」に書き、「採用後の振り返り」は「未評価」とします。
3. 下の一覧に追加し、関連する仕様・コード・Issue・PR があればリンクします。実装を伴う場合は原則として同じ PR に含め、大きな変更は ADR を先にレビューできます。
4. レビューでは「背景が明確か」「代替案を検討したか」「期待する効果や懸念が書かれているか」「仕様・実装と整合するか」を確認します。
5. メンテナーが判断したら、ステータスを「採用」または「不採用」にし、決定日（YYYY-MM-DD）と一覧を更新してマージします。不採用の場合も「決定と理由」に理由を残します。単独開発でも同じ記録を残します。

採用は実装完了を意味しません。未実装の作業があれば関連 PR や Issue に記録します。既存の設計を後から記録する場合は、その旨と確認できた根拠を背景に書きます。過去の決定日や理由が不明なら推測で埋めず、不明と明記します。

## ステータス

| ステータス | 意味 |
| --- | --- |
| 提案中 | 検討・レビュー中 |
| 採用 | 採用を決めた判断 |
| 不採用 | 検討したが採用しなかった判断 |

ステータスを変更したら、一覧も同じ変更に含めます。

## 採用後の振り返りと見直し

- 採用時点では「未評価」とし、実装・運用して分かった効果や問題、想定との違いを「採用後の振り返り」に追記します。予想ではなく、実際に確認できたことを記載します。
- 不採用の場合、振り返りは「対象外（不採用）」とします。
- 採用済みの判断を変えるときは、新しい ADR を作成します。新しい判断が採用されたら、双方の「関連リンク」に「置き換える ADR」「後継 ADR」を明記します。旧 ADR のステータスは「採用」のまま、当時の判断として残します。現在の方針は後継リンクをたどって確認します。
- 後継なく方針を終了する場合も、終了の判断と理由を新しい ADR に記録し、双方をリンクします。
- 元の背景や決定は当時の記録として残し、振り返りや関連リンクを更新します。誤字やリンクの修正は可能です。
- 文書の変更履歴は Git で管理します。ADR 本文に変更履歴や作成日は設けず、日付の項目は決定日のみにします。
